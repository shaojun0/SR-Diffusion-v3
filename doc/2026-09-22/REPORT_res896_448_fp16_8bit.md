## 0. 结论摘要（TL;DR）

1. **本轮最重要的结果不是 896，而是 448 那一臂：把原始配方换上 fp16 + 8-bit AdamW 后，训练快 3.26×，
   但"逐步精修"整块消失——曲线跨度从 −2.67 px 塌成 −0.07 px，与历史 `detach`（关掉 BPTT）对照臂的
   +0.07 px 在数值上已无法区分。** 绝对画质也从 16.42 掉到 18.04 px（+1.62 px / +9.9%）。
   ⇒ **fp16 + 8-bit AdamW 不是"免费加速"，它会改变优化落点；把它当默认口径前必须逐配置重新验证。**
2. **896 臂本身是"能精修、但码率轴崩了"**：12 步曲线真的在降（首→末 −2.82 px / −19.1%，逐 step 单调前缀 11/12），
   但整条曲线只覆盖 **0.005–0.329 bpp**（β=1 估计），在同 bpp 下**落后 WebP 最高 −11.25 dB、落后 JPEG −8.67 dB**。
   ⇒ 12 步的固定 token 预算（最多 145 token）对 45 万像素是**量级不够**，不是"再调调参"的问题。
3. 两个 896→448 的横向比较**都不能单独归因给分辨率**（见 §5 的变量表）：
   448 那臂同时改了 depth（2 vs 4）、步数（24 vs 12）、K/N（100% vs 7.3%）与精度口径。

## 3. 核心发现：fp16 + 8-bit AdamW 把 448 的"逐步精修"整块抹掉了

**同一份 448×252 / K=576 / 24 步 / d2 / BPTT 配方，三次运行只差精度与优化器**（n=3,004，同数据同步数同 seed）：

| | 历史 **fp32 BPTT** | 历史 **fp32 detach** | **本轮 fp16 + 8bit BPTT** |
|---|---|---|---|
| 像素 L1 (0-255) | **16.422 ± 5.86** | 23.719 | 18.04 ± 6.26 |
| 首步 → 末步 | 19.096 → 16.422 | 23.647 → 23.719 | 18.110 → 18.039 |
| **跨度（首−末）** | **−2.674（−14.0%）** | **+0.072** | **−0.071（−0.4%）** |
| 最优步 | 16.377 @ t=289（末步略回升） | 23.643 @ t=4 | 18.029 @ t=324 |
| 逐步曲线形态 | **真的下降**（前 2 步拿掉大部分） | **平**（后步甚至微升） | **平**（与 detach 同量级） |
| 首末步逐图 L1 跨图相关 | — | — | **0.9999** |
| 墙钟 | 4h36m50s（1.83 s/it） | — | **1h24m52s（0.58 s/it ⇒ 3.26× 快）** |
| 数据来源 | [`doc/2026-09-16/data/bptt24_bptt_infer_test.json`](../2026-09-16/data/bptt24_bptt_infer_test.json) | 同目录 `bptt24_detach_infer_test.json` | 本报告 `data/test_448_d2_bptt_fp16_8bit.txt` |

**图**：[`data/curves_448_precision.png`](data/curves_448_precision.png) —— 蓝（fp32 BPTT）从 19.1 陡降到 16.4；
灰虚线（fp32 detach）平在 23.7；**红（本轮 fp16+8bit）平在 18.0**。

**怎么读这张图（三句话）**：
1. **红线的"平"与灰线（detach）在形态上同类**：跨度 −0.07 vs +0.07 px，都远小于蓝线的 −2.67 px
   ⇒ **在 448 这个配置上，换上 fp16+8bit 之后，BPTT 带来的精修收益消失了**（`carry_detach=False` 一行没动）。
2. 但红线**不等于 detach**：它的绝对画质（18.04）远好于 fp32 detach（23.72），

   不是"退化成 detach"。
3. 训练期 `eval_recon` 轨迹两臂都收敛（§2）⇒ 这个平**不是欠训练**造成的。

## 4. 机制诊断：轨迹**在动但不降误差**（不是"输出不动"）

对一个"平曲线"，有两种完全不同的机制，必须分开：
(a) 各步输出**几乎不动**（carry 被忽略）；(b) 输出**在动**，但移动方向**不降误差**。
用 `tools/diag_step_spread.py`（8 张 test 图，0-255 全画布）直接量：

| 臂 | 末步 L1(GT) | 首→末改善 | \|首步−末步\| | 判定 |
|---|---|---|---|---|
| **② 448 fp16+8bit** | 14.49 | **+0.080** | 1.62 | **轨迹在动但不降误差** |
| **① 896 fp16+8bit** | 11.96 | **+2.819** | 7.78 | 轨迹在动**且降误差（真精修）** |
| 224 基线 fp32 | 9.21 | +0.780 | 3.65 | 弱精修（+8.5%） |

⇒ 448 这一臂**不是**"carry 断了/输出恒定"（那会给出 \|首步−末步\| ≈ 0），
它的步间增量是 **0.72 → 0.086 px 单调递减到零**、累计只挪了 1.62 px，
即**迭代收敛到一个"质量不比首步更好"的不动点**。
（三段原始输出：`data/diag_spread_out_{448_d2_bptt_fp16_8bit,896_d4_bptt_slice012,224_d4_bptt}.txt`）

**为什么 896 反而精修得好？** 两臂的差别不止步数（12 vs 24）：还有 depth（4 vs 2）与 K/N（7.3% vs 100%）。
最省的候选解释是"**fp16 下 BPTT 链越长、跨步的小梯度越容易被吃掉**"（24 步 vs 12 步），
但**本报告不主张这个机制**——它需要 §7 建议里的对照臂才能定。**目前只能确定现象，不能确定原因。**

## 5. 跨分辨率怎么读（**不能归因给分辨率**）

| | 224×126（历史） | 448×252（本轮） | 896×504（本轮） |
|---|---|---|---|
| 像素数 | 28,224 | 112,896（4×） | 451,584（16×） |
| K / N / 步数 / depth | 144/144/12/4 | 576/576/24/**2** | 168/2304/12/4 |
| 精度 / 优化器 | **fp32 / fused** | **fp16 / 8bit** | **fp16 / 8bit** |
| 像素 L1 | **12.02** | 18.04 | 15.85 |
| 最优 PSNR | **21.37** | 18.23 | 19.10 |
| MS-SSIM | **0.7731** | 0.5440 | 0.5864 |
| PSNR 跨度 | 0.30 dB | **0.01 dB** | 0.85 dB |

- 相对 224 基线：**896 在 16× 像素、只多 17% token（K 168 vs 144）的情况下，per-pixel L1 差 +3.83 px、PSNR 差 −2.27 dB。**
  这是"**token 预算相对分辨率不够**"的直接读数——但这 3.83 px 里也**混着 fp16/8bit 与 batch 口径的变化**，
  不能整块记到分辨率账上。
- **448 比 896 差（18.04 vs 15.85 px）不要读成"分辨率越高越好"**：448 那臂 depth=2、曲线是平的（§3），
  它是**另一种退化**，与 896 不构成干净的阶梯。**本仓库的 224/448/896 目前不是一条可排序的分辨率曲线。**

## 7. 诚实边界（**这几条不能省**）

1. **精度与优化器是一起换的**：② 的对照只说明"fp32+fused → fp16+8bit"这个**组合**的净效果，
   **不能**说成"fp16 造成的"或"8-bit AdamW 造成的"。要分离必须再跑 2 臂（见 §8）。
2. **448 的 bpp 轴与 896/224 不可直接同轴比较**：β=1 估计 `bpp = (t+1)·1024/px`，三者分母分别是
   112,896 / 451,584 / 28,224。**bpp–PSNR 可以同轴看形状，绝对 L1（0-255）不能跨分辨率比**。
3. **单 seed（42）、各跑一次、无误差棒**；② 与历史臂的 +1.62 px 差远大于噪声（历史同配方两臂 detach/BPTT 差 7.3 px），
   但"−0.071 与 +0.072 是否统计上同一"没有做检验。
4. **机制未定**（§4）：只知道 448 的轨迹"在动但不降误差"、896 的"在动且降误差"；
   "长 fp16 BPTT 链吃梯度"只是候选解释之一（还有 depth=2、K/N=100%、lr 口径等）。
5. **896 的 K/N=7.3% 是操作点性质的变化**：它不是"224 臂的放大版"（224 臂 K=N=144，100%）。
   本报告对 896 的所有结论都限定在"12 步 / K=168 / 45 万像素"这个操作点上。
6. **bpp 是 β=1 的估计**（tokens × 1024 bit / 像素），不是真实熵编码后的码率 ⇒
   与 codec 的 bpp 不是同一口径，只能当"乐观上界"看。
7. `oracle 自适应天花板` 两臂都 <0.12 dB ⇒ C2b 仍不成立，不要拿它做卖点。

## 8. 下一步建议（都要用户点头）

1. **分离精度 vs 优化器（最高优先，成本最低）**：在 448 配方上补 2 臂
   —— ①`fp16 + adamw_torch_fused`、②`fp32 + adamw_bnb_8bit`。
   若①也平 ⇒ 问题在 fp16；若②也平 ⇒ 问题在 8-bit AdamW；两臂各 ≈1.5 h（fp16）/ ≈4.6 h（fp32）。
2. **验证"链长"假设**：在 448 上把步数切到 `slice[0:12]`（K=168，与 896 同口径）跑 fp16+8bit，
   看精修是否回来。这一步同时把 §5 的分辨率阶梯补成干净的（448 与 896 只差分辨率）。
3. **896 的 token 预算**：896 要打 codec 需要显著更大的 K（例如 `slice[0:24]` ⇒ K=624，或直接 K=N=2304），
   代价是墙钟与显存；**当前 12 步口径下 896 没有 RD 竞争力，建议不要在这条线上继续投**，
   除非目标改为"极低 bpp 独占区"（896 在 ≤0.05 bpp 的点：t=1 是 0.005 bpp / 18.25 dB，codec 到不了这个码率）。
4. **把 fp16+8bit 从默认口径里撤出**，直到第 1 条有结论 —— 否则后续所有对照都会被这个未知项污染。
