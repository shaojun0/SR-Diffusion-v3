# 为什么曲线会平？——「纹理偏浅层」vs「解码器路由」两种解释的对照（2026-09-22）

> 缘起（用户提问）：**「纹理细节更偏浅层？对吗？」**
> 依据：[`doc/2026-08-27/DIAGNOSIS_clarity.md`](../2026-08-27/DIAGNOSIS_clarity.md)（项目自己的离线根因诊断）
> ＋ 本轮批 0 实测（[`REPORT_batch0_rd_earlystop.md`](REPORT_batch0_rd_earlystop.md)）。
> 本文**不引入新结论**，只做三件事：① 对齐 8-27 诊断与本轮实测；② **核对 8-27 建议的落地状态**；
> ③ 给出下一步的判别顺序。

---

## 0. 一句话

**用户的方向是对的**（最浅的 patch embed 不丢信息、高频是在中深层被语义化抹掉的），
**但根因排序不在这里**：8-27 诊断把**第一根因判给解码器的「逐 patch 信息路由缺陷」**（可回收 12.9 L1）。
而本文核对代码后发现：**该修法（P1-1/P1-2）至今从未落地**，判别用的 P0 探针也从未在新模型上跑过。

---

## 1. 用户假设成立的部分（有实测支撑）

`DIAGNOSIS_clarity.md` §3.4.1 原话：

> **patch embed 本身不丢信息，丢在 Transformer 语义化**：patch embed 是 kernel=14 的卷积（588→1024，
> 线性、可单射）；之后 24 层全局注意力把逐 patch 内容混合成语义 blob。

低通签名（§3.4.6，对重建图逐面板统计）：

| 指标 | 重建 / 原图 |
|---|---|
| 全局 std | **92–100%** |
| 块内（14 px）std | 79–99% |
| **邻域高频（边缘）** | **52% / 65% / 56%**（≈1/3） |

⇒ 能量与结构保住了，**丢的正是高频/纹理**。

**当前代码只用末层**（本文核对）：`model_v2.py:_encode_register` 跑完 DINOv2 全部 24 层 →
`self.dinov2.layernorm(seq)` → `return seq[:, :1], seq[:, 1:1+K]`。
**没有任何浅层 tap** —— 若纹理真在浅层，我们现在是 100% 丢弃。

---

## 2. 但根因排序（引 8-27 报告 §4）

| 优先级 | 根因 | 性质 | 可回收空间 |
|---|---|---|---|
| **1** | **OutputQueryDecoder 逐 patch 信息路由缺陷**（F1–F4） | 架构结构 | **22.7 → ≈9.8（12.9 L1）的大头** |
| 2 | DINOv2 语义特征信息上限 ≈9.8 | 结构性次因 | 决定"清晰"天花板 |
| 3 | PixelHead 单层线性 + 无空间归纳偏置 | 放大因子 | 部分锐度 |
| 4 | 纯 L1 损失（条件中位数 ⇒ 平滑） | 放大因子 | 观感 |

证据链核心：**真实 DINO 特征 → 线性解码像素 = L1 9.8**（对照：全图平均色 61.3），而当时模型全链路 = 23.4
⇒ **特征里还有信息，是链路丢了 13.6**。

F1–F4（本文逐条在当前代码上复核，**仍成立**）：

| # | 事实 | 当前状态 |
|---|---|---|
| F1 | special token k 的输入 = 共享 `token` + `pos[k]`，**无任何 patch k 内容** | ✅ 仍成立。`SpecialTokenBank` docstring 明写"**图像 patch 编码不进 decoder**" |
| F2 | 576 个 `z_s` 都是高度冗余的全局摘要（**加键不加信息**） | ✅ 仍成立（ReEncoder 已删，但 specials 仍只看全图） |
| F3 | 查询身份只来自**跨图固定**的模板 `query_base[k]` | ✅ 仍成立：`Y = query_base.expand(B,…)` → `stack(Y, A_in[lo:hi+1])` |
| F4 | 输出 = 共享键的凸组合 + 共享 FFN ⇒ 表达不出逐 patch 高频 | ✅ 仍成立（`K=V=A_in`） |

## 3. ⚠️ 8-27 建议的落地状态（本文新增，最有用的一节）

| 建议 | 状态 | 证据 |
|---|---|---|
| **P0 判别探针**（线性解码 `z_s`/`F_hat`） | ❌ **未做** | 从未在 register 式 / BPTT 模型上重跑 |
| **P1-1 逐 patch 内容查询**（`q_patch`） | ❌ **未做** | `grep q_patch model_v2.py` 无命中 |
| **P1-2 special 输入绑定 patch 特征** | ❌ **未做** | `SpecialTokenBank.forward = token + pos` |
| P2-1 PixelHead → MLP | ✅ **已做** | 现为 2 层 MLP `dim→2048→588`（~2.1M），不再是单层 Linear |
| P2-2 L1 + LPIPS | ❌ 未做 | 损失仍是纯 `mean_t L1(PixelHead(Y_t), target)` |
| P2-3 剔除 t=0 | ✅ 已做（等价） | `square_block_starts` 从 k=1 起 ⇒ steps=[1,4,9,…] |
| P3-1 分组 lr（DINO 低 lr） | ❌ 未做 | `TrainingArguments(learning_rate=args.lr)` 单组，无 `param_group` |
| P3-2 随机增强 | ❌ 未做 | `data_v2.py` 无任何随机增强（旋转是确定性函数） |
| P3-3 更高分辨率 | ⛔ 反向 | 本轮反而降到 224×126（用户口径，见批 0 报告 §10） |

> **结论**：8-27 报告排名**第 1、第 2** 的修法（P1-1 / P1-2）**都没做**，而排名第 3 的 P2-1 做了。
> 也就是说，**最大的那根杠杆一直没动过**。

## 4. 与本轮实测的一致性（复现，不是新发现）

| 现象 | 8-27 预言 | 本轮批 0 实测 |
|---|---|---|
| **t≥1 平台** | t=1: 22.93 vs t=576: 22.72，极差 0.213 = 可恢复空间的 **1.6%** | 448: L1 t=1 **19.10** → 最优 t=324 **16.38** → t=576 16.42；224: t=1 **12.67** → t=144 **12.02** |
| 加 token 无用 | 键冗余 ⇒ 加键不加信息 | 224 上 **72× 码率换 +0.30 dB** |
| 与像素量无关 | 缺陷在路由，不在像素 | 降到半分辨率后曲线**更平**（跨度 2.7 px → 0.67 px） |
| 自适应无空间 | — | E4b Δ ≤ +0.01 dB；oracle 凸包天花板 +0.129 dB（448） |

⇒ 本轮的两个配置（448×252 d2、224×126 d4）**都在复现 8-27 已经定位的同一个缺陷**。

## 5. 可回收空间的量级（**必须重测，勿直接引用**）

若 9.8 这个天花板在新模型上仍成立：

- **448×252**：当前 L1 16.42 ⇒ `20·log₁₀(16.42/9.8) ≈ **+4.5 dB**`（19.0 → 约 23.5 dB）
- **224×126**：**不能**用 448 的 9.8 去推 —— 天花板随分辨率变（目标更容易），必须单独重测

⚠️ 两个保留：
1. 9.8 是**旧模型（特征目标版）、448×252、32–64 张 in-sample** 的**上限估计**（8-27 §3.4.1 备注）；
   我们现在的模型是 **register 式 + BPTT + 像素目标**，数值可能不同。
2. 即便拿到 +4.5 dB，**仍然打不过 WebP**（批 0 §10.4：−5.3 ~ −15.9 dB），
   只是把"差 10 dB"变成"差几个 dB"。

## 6. 下一步（顺序不能颠倒）

1. **P0 判别探针**（~30 min，零训练，服务器）：分别测 `z_s → 像素` 与 `F_hat → 像素` 的线性解码 L1
   - `z_s ≈ 9.8` 且 `F_hat ≈ 16` ⇒ 信息丢在**解码器** ⇒ 做 P1-1
   - `z_s ≈ 16` ⇒ 丢在**编码器路由** ⇒ 做 P1-2（这也正是"纹理偏浅层"直觉的正式落法）
2. **P1-1 逐 patch 内容查询**：`Q = W_q(A_t) + query_base + q_patch(z_s[k])`（~5 行 + 1.05M 参数）
   8-27 预期 L1 22.7 → **≤16**，平台消失，边缘 1/3 → 60%+。
   现在重训只要 **~65 min**（224×126 / 8,760 步，见批 0 §10.1）。
3. **P1-2 special 输入绑定 patch 特征**：`token + pos[k] + Linear(patch_feat[k])`
   —— 不必让 24 层注意力去学"576 路路由"。
4. **最后**才上 LPIPS / 多尺度损失。8-27 §3.4.2 明确警告：**先修路由再加感知损失**，
   否则感知损失会逼模型"在没有信息的维度上编造锐边"（假细节）。

---

## 7. 边界（不要把本文读成"浅层无用"）

- "tap 浅层特征"**并非无效**，它是合理的候选；但它：
  ① 要**增加码率**（多一份 token 或加宽每 token），会改变 bpp 轴；
  ② 在当前证据里排在解码器路由**之后**（因为特征里的信息都还没被读出来）。
- 8-27 的 F1–F4 是在**含 ReEncoder 的旧架构**上写的；本文已逐条在当前代码上复核，
  结论是 **F1 / F3 / F4 仍成立**（ReEncoder 删除并未改变"specials 无 patch 内容 + 查询是固定模板"这两件事）。
- 本文所有"预期收益"都引自 8-27 报告，属**推断**，必须由 P0/P1 实测确认。
