## 1. 训练配置与结果

| 项 | 值 |
|---|---|
| 架构 | DINOv2-large(不冻结, 24 层全双向) + K=128 specials + DiT-lite 扩散解码器(54.3M) |

| 收敛 | eval_loss 0.1555 → **0.1193**（step 2000 → 8760） |

## 2. 推理测试（infer_v5.py, 全量 3004 张, DDIM 100 步, cfg_scale=1.0）

**口径注意**：v5 为条件生成（从纯噪声 DDIM 反向），与 v3/v4 确定性重建数值**不可直接对比**（参照：平均色≈61）。

### 2.1 全量重建 + token 消融

| 指标 | 值 |
|---|---|
| 全量 DDIM 像素 L1 (归一化) | **0.7203** |
| 全量 DDIM 像素 L1 (0-255) | **41.23 ± 10.12**（平均色 ≈61，改善 1.5×） |
| 无条件 DDIM L1 (token 消融) | 0.9043 |
| **token 价值** (条件 − 无条件) | **−0.184**（token 驱动了 0.184 的活信息还原） |

→ token 有信息（消融差距明显），但最终重建仅比"平均色"好 1.5× —— 纹理由扩散编造、结构保真度有限。

### 2.2 m 扫描探针（增量性直接判据, 固定噪声 t, 同一 ε）

| t | m=0 | m=16 | m=32 | m=64 | m=128 | Δ(m0→m128) |
|---|---|---|---|---|---|---|
| 250 | 0.1048 | 0.1045 | 0.1045 | 0.1045 | 0.1045 | −0.0003 |
| 500 | 0.1413 | 0.1410 | 0.1410 | 0.1410 | 0.1410 | −0.0003 |
| 750 | 0.1963 | 0.1958 | 0.1958 | 0.1958 | 0.1958 | −0.0005 |

**L1 随 m 解锁量几乎不变（Δ < 0.001）⇒ token 增量性未出现** —— 128 个 token 没有补新信息，信息仍堆在 z_cls + 首个 token（与 v2「悬崖+平台」同病：解码器对条件 token 的利用没有分工）。

### 2.3 渐进阶梯曲线（DDIM 每反向步）

| t | m | L1 (norm) |
|---|---|---|
| 1000 | 0 | 0.6008 |
| 495 | 65 | 0.7060 |
| 1 | 128 | 0.7203 |

阶梯曲线**不降反升**（末步 L1 > 首步）—— 与 m 扫描一致：解锁更多 token 没有带来阶梯式下降。设计预期的"粗→细"阶梯**未实现**。

## 3. 结论与归因

1. **训练本身正常收敛**（eval_loss 0.1193, 无 NaN/崩溃），扩散解码器学会了"从噪声 + 条件预测 x0"。
2. **token 有价值但无增量性**：消融差 0.184（条件确实驱动还原），但 m 扫描显示 L1 对解锁量几乎不敏感 —— **v5 的核心机制（NVAE 式渐进解锁 → 每个 token 补一层细节）没有生效**，信息仍集中在前置 token。
3. **可能原因**：
   - DINO 全双向 24 层下，specials 与 cls 位置已高度聚合全局信息，`z_s` 各 token 间冗余大（与 v2 的"信息摊匀"同源）；
   - `unlock=linear` 的 m(t) 随 t 线性变化，但训练时 t 随机采样，模型可绕过解锁约束（把信息塞进 z_cls/前几个 token 即可在所有 m 下工作）；
   - 扩散解码器对条件的使用是"平均聚合"（交叉注意力把所有 ctx token 加权求和），多 token 不改变信息量。
4. **与 v4 的关系**：v4 确定性重建做到 8.26 说明 K 压缩链路可读出；v5 换扩散后 L1=41（口径不同，但差距大），且**渐进性（v5 的灵魂）未达成** —— 用户"每 token 补细节"的思想在 v5 实现中仍未兑现。

---

## 4. 建议（下一步）

1. **验证解锁约束是否被绕过**：训练时记录各 m 下 token 的梯度范数/使用率（交叉注意力权重统计）—— 若 z_s[1:] 注意力权重≈0 则确认绕过。
2. **更强制的解锁**：`unlock=sqrt`（更早解锁更多）或对 z_s[i] 施加"只在 t 足够小时才参与损失"的硬掩码（而不是仅改条件输入）；或每个 token 绑定一个专属噪声子空间/频率带（强制分工）。
3. **编码器侧**：K 个 specials 加位置约束/正交正则，打破 z_s 间冗余（v4 的 register 思路可借鉴）。
4. **诊断先行**：跑一次"token 使用率"探针再决定是否继续调扩散，避免又一轮全量训练后才发现机制没生效。
