## 1. 口径（最终采用）

| 项 | 口径 |
|---|---|
| 图像统一 | **12:9 画布 1200×900**；横图按比例缩放后 letterbox 填充（灰底 127）；**竖图先顺时针旋转 90° 再填充** |
| 坐标 | 换算到画布像素后再归一化 **0–1000** 的 `[x1,y1,x2,y2]`（左上角为原点） |
| CoT 结构（detect/回归类） | 先 **spatial**（整幅空间结构：结构/区域/层次 + 方位 + 遮挡依附），再逐目标 **position**（落在什么结构的什么方位、依据），**最后拼接真值坐标** |
| CoT 结构（caption/vqa/classify） | spatial → evidence（关键视觉证据）→ 复述答案 |
| 粒度 | **每图一条 CoT**，覆盖该图所有框 |
| 语言 | 中文 |

> **关键设计决定**：坐标**不由模型生成**，而是由系统按真值拼接。模型只负责"为什么在这个位置"的推理。
> 原因：实测让模型复述坐标会出现 `[410,450],&[520,640]` 这类语法崩坏与截断（见 §4.1）。

## 2. 基础设施故障（必须记录）：本地 Qwen3.8-27B 视觉权重被抹零

**现象**：给模型一张木纹照片，它答"这是一张纯白色的空白图片"；给纯红图答"纯黑"；不给图时输出还会退化成无限重复。
**定位过程**：合成图对照（纯红/纯蓝/象限图）→ 模型恒定输出颜色词 ⇒ 怀疑图像通路；检查 `pixel_values` **正常**（std 0.36–0.74）⇒ 问题不在预处理；再查模型参数 ⇒ **`model.visual` 首个参数 std=0.00000**。

**根因**：`/root/autodl-tmp/models/Qwen3.8-27B/model-00001-of-00018.safetensors`（唯一损坏分片）中有 **33 个张量整层为 0**，包括：
- `model.visual.patch_embed.proj.weight`（像素→token 的入口层，形状 1152×3×2×16×16）
- `model.visual.blocks.11/12.*`（整块）
- `model.language_model.layers.1.linear_attn.norm.weight`

其余 17 个分片干净（抽样扫描 1199 个张量，仅 shard 1 的 33 个全零）。下载日志显示当时走的是 **ModelScope**（`Qwen/Qwen3.8-27B`），`dl_hf.log` 里有中断报错记录。

**修复**：从 ModelScope 重下该分片（`curl -L --fail -C -`，3,966,730,552 B），校验 0 个零张量后替换；旧文件保留为 `model-00001-of-00018.safetensors.bad`（4 GB，可删）。
**修复后验证**：纯红→"红色"；木纹→"一块带有清晰木纹的浅色木板"；实拍→"一名戴黄色安全帽的建筑工人正在工地上使用锤子进行作业" ✓

> ⚠️ **此前用这个模型做过的一切"多模态"结论都不可信**（它当时是文本模型）。纯文本翻译不受影响（语言权重只在 shard 1 的一个 norm 被抹零，且实测译文正常）。

### 4.1 第一版失败的三种模式（已修）

1. **JSON 截断**：要求"spatial + 每目标 position + 坐标 + 再串一遍 cot"输出过长，`max_tokens=800` 被耗尽。
2. **坐标语法崩坏**：模型复述坐标时写出 `"bbox":[410,450],&[520,640]`、`[652,489],688],534]`。
3. **退化重复**：一条 hf-vision 样本把同一句"中央偏右区域被上方与下方延伸的开阔空间所依托…"重复了数百遍，直到 token 耗尽。

**修法**：① 不让模型输出坐标（系统拼接）；② 删掉重复的 `cot` 字段；③ 缩短 `objects` 每项长度上限。修后 detect 解析 100%。

## 5. A/B：坐标作为"定位线索"（本轮最重要的质量提升）

同一批 4 个 detect 数据集（400 条），只改提示词：

| dataset | v1 不给坐标 | **v2 给出真值坐标作为定位线索** |
|---|---:|---:|
| `aswin00000` | 93 / 100 = 93% | **98 / 100 = 98%** |
| `baizhanquan` | 88 / 100 = 88% | **100 / 100 = 100%** |
| `hf-vision` | **54 / 100 = 54%** | **99 / 100 = 99%** |
| `iluvvatar` | **60 / 100 = 60%** | **100 / 100 = 100%** |
| **detect 合计** | **295 / 400 = 73.8%** | **397 / 400 = 99.25%** |

**机制**：同一张图里同类目标共用同一句标签时（例如 aswin 一条 rule 关联两个框、hf-vision 一图 8 个 helmet），不给坐标模型无法区分谁是谁，实测会把左右方位**说反**。给出坐标后模型能"按坐标找位置再描述"，错误几乎消失。

## 6. DeepSeek 视觉复核

**先验证 DS 真的能看图**（合成图）：纯红→"红色"、纯蓝→"蓝色"、白底左上角红块→"左上" ✓（`deepseek-v4-pro` 拒绝图片，只有 `deepseek-flash` 支持）。

判据：`spatial_ok`（空间结构是否与图相符）、`align_ok`（每个目标的方位/结构是否与图+坐标相符）、`invented`（是否描述图上不存在或真值之外的目标）、`coord_ok`（方位词与坐标是否矛盾）；判决 `pass / minor / fail`。

**判决抖动**：同一批 400 条两次复核，**不一致 3 条 = 0.8%**，且都是"第一次 fail、第二次 pass"⇒ 采用**两次取严**的保守口径。

## 8. 局限（诚实登记）

1. **竖图旋转会让内容侧倒**：63 张竖图被旋转 90°，模型有时会直接写出"画面为旋转90度的施工现场"。DS 是对着同一张旋转后的图复核的，所以能通过——但作为训练数据，这是"侧着的画面"。**是否保留旋转需你确认**；若不要，改成纯填充即可（改一行）。
2. **只有单一复核模型**，且判决有 0.8% 抖动；没有第二模型交叉。
3. **只做了 7/11 个数据集**：`Voxel51/hard-hat`（FiftyOne）、`keremberke/hard-hat`（zip 内 YOLO）、`fireviewer`（图在盘上）、`MVTec-4K`（jsonl + 掩码）尚未纳入（容器形态不同，需要额外 reader）。
4. **每数据集仅 100 张**，未验证放量后的稳定性与成本。
5. 三个 UNKNOWN 标签数据集仍无映射（`flame2`、`hiennguyen9874`、`SRuibo`），无法生成语义正确的 CoT。

## 9. 建议下一步

1. **放量**：先按 21 个数据集 × 1000 张估算（生成双卡约 X 小时、DS 复核约 Y 万 token），确认成本后再全量。
2. **补齐 phase 2 的 4 个数据集**（需要写 4 个 reader：FiftyOne JSON / zip 内 COCO / 磁盘图片+parquet 索引 / jsonl+掩码）。
3. **确认竖图策略**：保留旋转 vs 纯填充（影响 63/700 ≈ 9%）。
4. 3 条 fail 可作为提示词迭代的种子样例。
5. **把"Qwen 视觉权重被抹零"写进交接文档**——这是个会静默毁掉所有多模态实验的坑。
