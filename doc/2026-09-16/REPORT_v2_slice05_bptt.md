# slice[0:5] + BPTT 臂（2026-09-16）

> 配套文档：[`REPORT_v2_bptt_vs_detach.md`](REPORT_v2_bptt_vs_detach.md)（**24 步全轨迹**的 detach vs BPTT 对照）
> 本文回答的是另一个操作点：仓库"后步坍缩 / 零增量自锁"那条线真正使用的 **slice[0:5] → K=35 → 5 步** 配置。

## 0. 结论（TL;DR）

| 指标 | 历史 slice05 基线（2026-09-10） | 本次 slice05 + BPTT |
|---|---|---|
| 配置 | 并行架构 `d72e5eb`、blockdiag、**累加损失口径**、单卡 bs=32 | 循环架构 `033cb27`+patch、**直接预测口径**、2 卡 bs=16 |
| 全量 test `full_norm_l1` | 0.3318 | **0.314064**（−5.3%） |
| 全量 test 像素 L1 (0–255) | 19.02 | **18.05 ± 6.50**（−5.1%） |
| 逐步 L1（5 步） | — | 18.27 → 18.03 → 18.05（**仅改善 1.3%**） |

**三条要点：**

1. **最终重建比历史基线略好**（−5.3%），但这是**跨代 + 跨损失口径**的对比（见 §4），只能算提示、不能算归因。
2. ⚠️ **在 slice05 上"后步真干活"并没有出现**：逐步 L1 从 18.27 只降到 18.03（**1.3%**）且末步回升；
   作为对比，同一份 BPTT 在 **24 步全轨迹**上后步改善 **14.2%**（19.10 → 16.38）。
   ⇒ 5 个步基本在做同一件事（各自预测整图，质量几乎相同）。
3. ⚠️ **`DESIGN_v2_recurrent.md` §6 判据①（`step_px_scale`）在现行损失口径下已失效**，
   本次实测全为 ≈1.03（= 目标量级的 91.5%），这是**直接预测口径的结构性结果**，不是"坍缩被打破"。详见 §3 —— 这是本轮最值得记下的方法学结论。

## 3. ⚠️ `step_px_scale` 不能再用来判断坍缩（判据①失效）

`DESIGN_v2_recurrent.md` §6 判据①写的是"后步量级：`probe_step_collapse.py` 的 `step_px_scale`
应显著脱离 `[~1, ~0.04, ~0.03, …]`；目标 = 后步 `> 0.015`"。本次实测：

| | `step_px_scale` |
|---|---|
| 本次 slice05 + BPTT（原始值） | `[1.03246, 1.03658, 1.03897, 1.03959, 1.03985]` |
| 本次 slice05 + BPTT（÷首步） | `[1.0, 1.004, 1.006, 1.007, 1.007]` |
| 旧值（2026-09-10，blockdiag，**累加口径**） | `[1.0273, 0.0395, 0.0349, 0.0342, 0.0335]` |

**为什么这里 ≈1 而不是"坍缩被打破"**：实测同一批数据上

```
mean|target_pix|        = 1.14150
mean|Y_pix| (所有步平均) = 1.04487   ( = 目标的 91.5% )
```

当前损失是 `mean_t L1(PixelHead(Y_t), target)` —— **每一个采样步都被直接监督去预测整图**，
所以每步输出的量级**必然** ≈ 目标量级，与"这一步是否做出了别的步做不到的贡献"**无关**。
旧值 `[1.03, 0.04, …]` 之所以有判别力，是因为它测的是**累加口径下 `Y_t` 作为"增量"**的量级，
后步增量≈0 才等于"后步没干活"。

⇒ **2026-09-15 把损失从"累加"改成"直接预测"时，这条判据被静默作废了**（数值全被抬到饱和 ≈1）。
现行口径下唯一有判别力的量是**逐步 L1 是否递降**（本文 §2.3 用的就是它）。
§6 判据①需要改写；`probe_step_collapse.py` 也应同步（它现在还传已删除的 `query_mask_mode`，
在当前代码上直接 `TypeError`，本次因此没有用它，而是按同一口径自行重算）。

## 4. 怎么解读这次结果

1. **能说的**：在 slice05 上，BPTT 版（循环 + 直接预测）最终重建优于 2026-09-10 的历史基线约 5%。
2. **不能说的**：这个 5% **不能归因给 BPTT**。历史基线是**并行架构 + 累加损失 + blockdiag**，
   与本次（循环 + 直接预测 + BPTT）在**架构、损失口径**两处都不同 ⇒ 跨代对比，只能算"没有变差、且略有提示"。
3. **最重要的负面结果**：即使在 BPTT 下，**slice05 的后步仍然没有分工**（1.3%）。
   这与 24 步全轨迹（14.2%）形成鲜明对比，说明"后步是否真干活"**强依赖操作点**，
   不能拿全轨迹的结论去回答 slice05。

**可能原因（推断，未验证）**：K=35 时每步读到的块非常小（`block` 首步 4 列、末步 11 列，
见 `DESIGN_v2_recurrent.md` §5 实测），后步可读到的增量信息本就有限；也可能 5 步太短，
细化还没展开就结束了。

## 5. 边界

1. **没有同代码控制臂**：未跑"当前代码 + slice05 + detach"，所以 BPTT 在 slice05 上的净效应无法干净归因
   （用户本轮选择只跑 BPTT 臂以省时间）。补这一臂约 1.5 h。
2. **单 seed（42）**，无误差棒。
3. 未使用 `probe_step_collapse.py`（见 §3 末，其对当前代码不兼容）。
4. 历史基线本身**非单调**且为单 seed（`REPORT_v2_blockdiag_slice05.md` §3 自述），其 0.3318 的可靠性有限。

## 6. 建议后续

1. **补 slice05 + detach 的当前代码控制臂**（~1.5 h）⇒ 才能把 §2 的 5% 干净地归因给 BPTT。
2. **修 `DESIGN_v2_recurrent.md` §6 判据①**（以及 `probe_step_collapse.py` 的口径），
   换成"逐步 L1 递降"类指标；否则后来人会继续拿一个饱和的指标当坍缩探测器。
3. 若目标是让 slice05 的后步真正分工，BPTT 只解决了"梯度通路"，还需要 **P1 分区掩码损失**
   制造"step-1 抢不走的私有目标"（`doc/2026-09-07/DESIGN_v2_region_loss.md`）——
   且该实验**本来就该在 slice05 上做**。
